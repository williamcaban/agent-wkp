# Implementation milestones

Each milestone has an exit criterion that is observable, not a checklist of files. A milestone is done when its exit criterion holds on `main` with CI green. Issues carry the `M<n>` label. Order is strict: M1 replaces the Python tool for daily use before any sync or hub work starts, so every later milestone is dogfooded on a real store.

| Milestone | Theme | Exit criterion |
|---|---|---|
| M0 | Foundations | `wkp --version` builds as a static binary on macOS arm64 and Linux x86_64 from a clean checkout; CI runs fmt, clippy, test, audit, deny, bench; binary under 10 MB; minimum git version decided and enforced at runtime |
| M1 | Read path parity | On the author's real store, `wkp init`, `index`, `search`, `context`, `materialize`, `hooks --framework claude_code` work end to end; Claude Code SessionStart hook injects Tier 0; latency targets in design 4.3 met on the bench corpus; Python tool no longer used day to day |
| M2 | Write path and audit | `wkp remember` produces SSH-signed plumbing commits with provenance trailers; agent writes land in `inbox/`; `wkp promote` requires a human-signed commit; injection-corpus test passes; gitleaks rules block credential-like content |
| M3 | Local sync | Two machines and a plain bare repo (NAS or GitHub) stay in sync through `wkpd` per-device branches; the `wkp` merge driver resolves modify/delete and add/add without data loss; `git bundle` round trip works air-gapped; unsigned or unknown-signer commits are excluded from Tier 0 and 1 |
| M4 | Encryption | `visibility: private` items are age-encrypted in git via clean/smudge; keys live in macOS Keychain or Linux secret-service with ssh-agent fallback; recovery key flow; `wkp forget` rotates recipients; `wkp purge` documented and tested |
| M5 | Hub | Container with sshd + `wkp-shell` + `git http-backend`; per-tenant hard isolation (a container-runtime pod per tenant, ADR-0009 — supersedes the original "per-tenant UID" wording), bare repo and SQLite index; RFC 8628 device registration; device revocation effective on next connection; integration test: register, push, revoke, push-must-fail |
| M6 | Hardening and release | Landlock + seccomp on Linux, sandbox on macOS verified; cosign-signed reproducible releases with SLSA provenance and SBOM; Homebrew tap; OCI image; OpenSSF Scorecard gate; self-update verifies signatures |

## M0 tasks

1. Scaffold the Cargo workspace per design 3.3 with `rust-toolchain.toml`, release profile (`lto = "fat"`, `codegen-units = 1`, `panic = "abort"`, `strip = true`), `deny.toml`, `supply-chain/` for cargo-vet, `#![forbid(unsafe_code)]` everywhere except `wkp-sys`.
2. CI baseline: fmt, clippy `-D warnings`, test, `cargo audit`, `cargo deny`, `cargo vet`, Semgrep with the Rust ruleset, actions pinned by SHA, least-privilege `permissions:`.
3. Git minimum-version spike: confirm SSH signing (`gpg.format=ssh`, `gpg.ssh.allowedSignersFile`) and builtin fsmonitor behavior on the current macOS and Fedora git builds; record the decision as ADR-0001; `wkp` refuses to run below the minimum with a clear message.
4. Remove the Python tree from this branch after tagging `v0-python` on `main`; keep `AGENTS.md` (to be rewritten in M1) and `LICENSE`.
5. Benchmark harness: criterion benches for cold `wkp search`, incremental index, materialize; a fixture corpus generator (5k and 50k items); `benches/baseline.json` and a regression threshold documented in `benches/README.md`.
6. Cross-compile and static-link check: `x86_64-unknown-linux-musl`, `aarch64-apple-darwin`; size gate.

## M1 tasks

1. OKF frontmatter parser with the v2 fields (`scope`, `provenance`, `confidence`, `expires`, new `type` values); tolerant of missing or malformed frontmatter; fuzz target.
2. Index: bundled SQLite with FTS5, schema from design 5.3 (porter unicode61 content column, trigram column for identifiers, metadata columns), atomic swap of `index.db`.
3. Change detection via `git update-index --refresh` + `git status --porcelain=v2`, fsmonitor when available; hash only changed files.
4. `wkp search` with BM25, tier and budget filters, `--format paths|text|json`; cold-start budget enforced by bench.
5. `wkp context` and `wkp traverse` parity with the Python behavior (graph edges from `refs:` and wikilinks).
6. `wkp materialize --tier 0|1` with atomic write; `wkp hooks --framework claude_code` prints hook text only.
7. Importer for `~/.claude/projects/*/memory/`, `CLAUDE.md`, `AGENTS.md` tagged `source: import`.
8. Golden tests for `tier0.md` output; rewrite `AGENTS.md` for the v2 CLI.
9. Optional hybrid search via `--embed-url` with RRF and BM25 fallback, kept out of the default path.

## M2 tasks

1. Identity model and `allowed_signers` (design 7.3): the file format the store carries mapping a principal (`human:<id>` / `agent:<harness>[:<model>]`) to a `role` (`human`/`agent`) and an SSH public key; `wkp-git` plumbing to read and append entries; `wkp init` wires `gpg.format=ssh` and `gpg.ssh.allowedSignersFile` to point at it. Out of scope: OS keystore/Keychain ACL integration for agent private keys (that lands alongside M4's keystore work); this task assumes a key is already available to `ssh-agent` or referenced by path.
2. Signed plumbing commit wrapper in `wkp-git` (design 5.1, 7.3): a real SSH-signed commit primitive (plumbing, not the porcelain `commit_all` M1 left as a test-only placeholder) that takes a caller-specified identity (a principal from task 1), stages the given paths, and produces a commit `git verify-commit` accepts. Replaces `commit_all`'s doc-comment TODO.
3. Provenance trailers (design 5.4, 7.4): a commit-message trailer format (actor, session, source, confidence) appended by task 2's wrapper, plus a parser that reads them back off a commit for provenance queries.
4. Gitleaks-style secret detection on the write path (design 7.6): a compact, bundled ruleset (regex + entropy checks, evaluated in-process, no shelling out to a `gitleaks` binary) that refuses content matching a credential pattern and returns a redacted preview.
5. `wkp remember` (design 7.4, 7.6): reads content from stdin (never argv, per CLAUDE.md's secrets rule) plus minimal frontmatter fields, runs task 4's scan first, writes the file under `inbox/<slug>.md` with `confidence: proposed` and `provenance.source`, commits it via task 2/3's signed-plumbing-plus-trailers path.
6. Real provenance-gated tier computation (design 7.4), replacing `wkp_core::index::compute_tier`'s M1-4 type/confidence placeholder: Tier 0/1 requires the item's latest commit to be signed by a `role: human` principal (task 1), plus the `type: instruction` path-scoping rule from 7.4. Also closes the `expires` gap noticed auditing M1: an item whose `expires` date has passed is excluded from Tier 0/1 the same way an `inbox/`/agent-confidence item already is (design 5.4 says the indexer does this automatically; M1 never wired it in). Out of scope: verifying commits that arrive via sync/fetch from another machine (`wkp verify`, a fetch-time gate) — that is M3's "unsigned or unknown-signer commits are excluded from Tier 0 and 1" exit-criterion line, not this task's; this task's gate applies regardless of a commit's origin, sync just doesn't exist yet to originate one.
7. `wkp promote <path>` (design 7.4): moves an `inbox/` item into the durable tree (`user/`, `projects/<name>/`, `org/<name>/` per the 5.4 layout convention) with a human-signed commit; refuses when the calling identity isn't `role: human`, except for a harness explicitly configured `promote: auto` (7.4's documented, opt-in, not-default escape hatch).
8. Injection-corpus test suite (`tests/injection-corpus/`, CLAUDE.md: "there is a test for this; do not weaken it"): adversarial fixture stores (unsigned commits, wrong-role signers claiming `type: project-state`/`instruction`, prompt-injection payloads in otherwise-valid frontmatter, `inbox/` items claiming a tier-0 type) with a test asserting `wkp materialize --tier 0|1` never includes any of them — the regression gate for tasks 6 and 7 together.

M2's exit criterion holds on `v2-rust` as of all eight tasks above merging (issues #37-44, PRs #46-53). M3 tasks below are broken out per that.

## M3 tasks

**Scope note on "wkpd" in this milestone's own exit criterion**: design 4.2 is explicit that `wkpd` is optional convenience (file watching, scheduling) layered on top of subprocess commands that already work standalone. Tasks 1-3 below build the actual sync mechanism as a synchronous, on-demand `wkp sync` subcommand — no daemon, no file watcher — which is sufficient to demonstrate "two machines... stay in sync" for this milestone's exit criterion. Task 8 adds `wkpd` itself (watch-triggered automation calling the same `wkp sync` logic), so the milestone's own literal wording is still honored, just not load-bearing for the core guarantee.

1. Per-device identity and `sync/<device-id>` branches (design 4.2, 6.2 point 1: "avoid" via unique refs so two machines never write the same ref): a device ID generated once and persisted (e.g. `.wkp/device-id`), plus `wkp-git` plumbing to create/checkout/commit onto a per-device branch. Foundational for every later task in this milestone.
2. Custom git merge driver for OKF frontmatter (design 6.2 point 2): `wkp merge-driver` implementing git's merge-driver protocol (`%O`/`%A`/`%B` temp files), safe-mode semantics for the cases git's own three-way merge can actually hand it (add/add on the same path, frontmatter field conflicts within a modify/modify): union of `tags`, max of `updated`, keep both `provenance` entries, keep both bodies with provenance markers on an unresolved body conflict. `wkp init` writes the `.gitattributes` entry (`*.md merge=wkp`) and registers `merge.wkp.driver` in local config.
3. Modify-vs-delete safe-mode handling (design 6.2's safe-mode rule: "a deletion always loses to a modification"): git's merge machinery stops with `CONFLICT (modify/delete)` **without** invoking any content merge driver for this case, so this needs its own detection-and-resolution step (a post-merge scan via `git status`/`ls-files -u`, or an equivalent pre-merge pass): keep the modification, re-propose the deletion as a new `inbox/` item for a human to confirm — never silently drop content.
4. `wkp sync`: `git fetch` from a configured remote, merge every other device's `sync/*` branch (and `main`) into the local device branch using tasks 2/3, push the local device branch. Merging a device branch into `main` itself still needs a human-signed commit or `wkp promote` (M2-6/M2-7's provenance rules apply unchanged — an auto-committed device-branch change doesn't gain tier 0/1 just by landing in history).
5. `git bundle` round trip for air-gapped sync (design 6.1): `wkp bundle export <path> [--since <ref>]` / `wkp bundle import <path>`, wrapping `git bundle create` / `git bundle verify` plus fetch.
6. `wkp sync status` (design 6.2 point 3, "ask"): surfaces conflicts tasks 2/3 couldn't auto-resolve, as an explicit, harness-actionable report.
7. Fetch-time signature reporting: M2-6's `compute_tier` already excludes unsigned/unknown-signer commits from tier 0/1 regardless of a commit's origin (confirmed when M2-6 was built — no new gating logic needed here for the tier-gate itself to hold across sync). This task is purely human-facing visibility: after a `wkp sync`/fetch, report which newly-arrived commits are unsigned or from an unknown signer, so a human notices rather than content silently sitting at tier 2 with no explanation.
8. `wkpd`: watch-triggered automation (design 4.2's cycle: OS file watcher → debounce → incremental re-index → task 1's per-device auto-commit → task 4's `wkp sync`) over a Unix domain socket (mode `0600`, peer-UID verified, never a TCP port). A thin wrapper around tasks 1-4's already-standalone logic, not new sync logic of its own.

M3's exit criterion holds on `v2-rust` as of all eight tasks above merging (issues #54-61, PRs #63/#64/#65/#66/#67/#68/#69/#70/#72 — #70 was an unrelated, explicitly requested source-file modularization refactor that landed in the middle of this milestone's work, #71 a one-line `deny.toml` license allow-list change split out of #72 per this repo's own rule against combining that file with feature code). M4 tasks below are broken out per that.

## M4 tasks

**Scope notes, found while breaking this milestone down (verified by hand — a throwaway `age`-crate round-trip test — before writing these, not assumed from the design doc alone):**

- The `age` crate (design 7.2's chosen library) pulls in a real dependency tree regardless of feature flags — `default-features = false` does not trim it, because the size comes from `age` itself unconditionally depending on an i18n/error-message-localization stack (`fluent`/`i18n-embed` and friends), not from anything gated behind a feature. Task 1 below must measure the actual binary-size and `cargo vet` impact before merging and, if it's material, write an ADR on whether to accept it, vendor a narrower age implementation, or gate `wkp-crypto` behind a non-default feature the way M1-9 gated `--embed-url` — unlike hybrid search, encryption for `visibility: private` items is not something a user can opt out of per-item, so a feature gate here would need its own careful thought about what a build without it can and cannot do.
- Design 7.2/7.5's "keys live in macOS Keychain or Linux secret-service with ssh-agent fallback" describes SSH signing key storage (design 7.3) applied by analogy to age identities, but an age X25519 identity is a *decryption* key, not something `ssh-agent` (an SSH-agent-protocol signer) can hold or produce output from the way it holds signing keys. Task 2 below needs to resolve this design/reality gap explicitly (most likely: `ssh-agent`/an SSH key only ever signs commits per design 7.3, and the *encryption* identity is always keystore-or-file-backed with no ssh-agent-shaped fallback at all) and record the resolution as an ADR rather than silently reinterpreting the design text.
- Design 7.6's one sentence about `wkp forget` ("removes the file and, for private items, rotates the age recipients so old ciphertext becomes unreadable to revoked devices") reads as two related but distinct operations — deleting one memory item, and revoking a *device's* access to every still-existing private item — compressed into one sentence. Task 5 below should resolve which `wkp forget` actually does (or whether it is in fact two things under one name, e.g. `wkp forget <path>` vs. `wkp forget --device <id>`) and document the choice, rather than guessing silently.

1. Age encryption core in `wkp-crypto` (design 7.2): X25519 identity/recipient types and `encrypt(plaintext, recipients) -> ciphertext` / `decrypt(ciphertext, identities) -> plaintext`, using the `age` crate in-process (no shelling out). Pure functions with no git or keystore involvement yet — the primitive layer every later task builds on. Verify and record the binary-size/`cargo vet` impact noted above.
2. Device encryption identity + OS keystore integration (design 7.2, 7.3): generate a device's X25519 identity on first use; store the private key in macOS Keychain or Linux secret-service. Resolves the `ssh-agent`-fallback scope note above via its own ADR.
3. Recipients file + recovery key (design 7.2 accepted failure modes): a per-store file listing every registered device's X25519 public key plus an optional recovery public key (parallel in spirit to `allowed_signers` — tracked, not itself encrypted), generated at first use and shown once. Needed before task 4, which must know who to encrypt to.
4. git clean/smudge filter for `visibility: private` (design 7.2, 5.1): `wkp` registers as a git filter driver (`.gitattributes: *.md filter=wkp-crypt`, `wkp init` wiring `filter.wkp-crypt.clean`/`.smudge` in local config, the same self-invocation pattern `wkp merge-driver`, M3-2, already established). Clean direction parses the incoming content's frontmatter and encrypts the whole file to the current recipient list only when `visibility: private`; smudge direction detects age's own recognizable ciphertext header and decrypts only when present. Both directions are a cheap pass-through for every `shared` file.
5. `wkp forget <path>` (design 7.6): removes an item, resolving the scope note above.
6. `wkp purge` (design 7.6): a wrapped, documented `git filter-repo` procedure for true history erasure, plus the forced-push-and-re-clone-on-every-device instructions surfaced clearly to the user. "Tested" per this milestone's exit criterion means the local half (invoking `filter-repo`, verifying the target path is actually gone from history) — the multi-device re-clone step is inherently a real-world, multi-machine operation this repo's CI cannot exercise.

M4's exit criterion holds on `v2-rust` as of all six tasks above merging (issues #73-78, PRs #80/#81/#82/#84/#86/#88, plus #85 and #87 — small CI-gate fixes split out per this repo's own rule against combining `.github/workflows/*` changes with feature code). M5 tasks below are broken out per that.

## M5 tasks

**Scope notes, found while breaking this milestone down:**

- Design 8.2 mentions billing delegated to a Merchant of Record (Paddle or Lemon Squeezy). This milestone's own stated exit criterion (container with sshd + `wkp-shell` + `git http-backend`; per-tenant UID, bare repo and SQLite index; RFC 8628 device registration; device revocation effective on next connection; one integration test: register, push, revoke, push-must-fail) never mentions billing at all. Deliberately out of scope for every task below — a later, separate product decision (which MoR, pricing), not a CI-testable milestone gate.
- RFC 8628's device grant flow needs a human-facing verification page (where a user enters the short code and approves), but design 3.3 explicitly places the account/billing web app in "a separate repo... if and when it exists," walled off from tenant content. Resolution: for this milestone, the hub binary itself serves a bare-minimum verification page as part of the control plane (task 2) — good enough for the exit criterion's own CI-driven integration test — not the eventual product-quality web app, which remains out of scope here.
- Design 8.2 says the control plane's Postgres can be "Supabase or RDS" — real hosted accounts. This milestone's exit criterion only needs something CI can stand up and tear down itself (a Postgres service container in the CI job) to prove the schema, the device-grant flow and revocation actually work; provisioning a real hosted instance is later, separate deployment work this task list does not cover.
- Design 8.1 names two transports: SSH (`sshd` + `AuthorizedKeysCommand` + `wkp-shell`) and HTTPS (`git http-backend` behind a reverse proxy validating a device-scoped bearer token). The milestone's one required integration test (register, push, revoke, push-must-fail) is scoped to the SSH path only, below (task 5) — it is D7's primary transport and the simpler one to exercise in CI without also standing up TLS termination and bearer-token issuance. The HTTPS path (task 6) gets its own, independent test coverage rather than folding into that one required test.
- **Per-tenant hard isolation is a container-runtime pod per tenant (ADR-0009), not Unix-UID separation inside one shared container, and not `podman exec` from the front door into a tenant's pod** (rejected: no Kubernetes equivalent for a running service to exec into another pod on its own hot path). The front door reaches a tenant's pod over the network, speaking git's own smart-HTTP protocol against that pod's `git http-backend` — the same backend 8.1 already picked for the HTTPS transport, reused here so there is one per-tenant backend implementation, not two. Task 5 below is rescoped to the front-door container only, against a single shared filesystem; the pod-per-tenant model itself is task 7, a follow-up this milestone's exit criterion does not close without.

1. Control-plane schema and Postgres client (design 8.2): tenants, devices (public key, `revoked_at`) and device-grant (RFC 8628 pending/approved codes) tables in `wkp-hub`, behind a real Postgres client crate — new dependency, needs its own justification, `cargo deny`/`cargo vet` pass in the PR per CLAUDE.md. CI runs this against a Postgres service container, not a hosted instance (see scope note above). The foundational piece every later task in this milestone builds on.
2. RFC 8628 device authorization grant (design 6.4, 8.1): control-plane HTTP endpoints for the device/token exchange, plus the minimal verification page resolving the scope note above; `wkp hub register` (CLI side) polls per RFC 8628, generates an ed25519 device identity via the OS keystore (same storage pattern M4-2 already established for the encryption identity, applied here to a signing key), and uploads only the public key. Test: a scripted stand-in for the human "click approve" step (a direct HTTP POST to the verification endpoint) driving a full register round trip against task 1's schema.
3. `wkp-shell`: key-to-tenant mapping for `sshd`'s `AuthorizedKeysCommand` (design 8.1), restricting the resulting `command=` to only `git-receive-pack`/`git-upload-pack` on that tenant's own bare repo — refuses an unknown or revoked key, and refuses any command that isn't one of those two. **Human co-sign required**: design 9.1 names "the hub's key-to-tenant mapping" explicitly as one of the changes that always needs one. Tested at the Rust logic layer (given a key and the control-plane state from task 1, what `command=` line comes out, or that nothing does); real `sshd` wiring is task 5's job, not this one's.
4. Per-tenant bare repo, SQLite index and post-receive indexing (design 8.2, 8.3): provisioning a tenant's bare repo with `receive.fsckObjects=true`/`transfer.fsckObjects=true`, and a `post-receive` hook that runs `wkp index` against the pushed `shared` (plaintext) subset only into that tenant's own `index.db` — never touching `visibility: private` content, which stays ciphertext the hub never has a key for. Test: a real bare repo and hook fixture, a real `git push` into it, confirming the hook ran and only shared content landed in the index.
5. Front-door container image (sshd + `wkp-shell`, design 8.1/8.3) and this milestone's one required integration test, against a single shared filesystem — **not** the pod-per-tenant model (task 7). `sshd_config` hardening per 8.1's list (`PermitRootLogin no`, `PasswordAuthentication no`, `AllowAgentForwarding no`, `AllowTcpForwarding no`, `PermitTTY no`, `ed25519`-only, `AuthorizedKeysCommand` wired to task 3, `AuthorizedKeysCommandUser` set to a dedicated low-privilege user per `sshd`'s own requirement for that directive). Base image: Fedora (`quay.io/fedora/...`), built and run with `podman`. **Human co-sign required** (container/sandbox-adjacent surface, design 9.1). Integration test, run against the built container image in CI: register a device (task 2), push over SSH (tasks 3/4), revoke it (task 1's control plane), attempt another push, confirm it fails -- `sshd` re-evaluating `AuthorizedKeysCommand` on the next connection is what actually makes revocation effective, not anything client-side.
6. HTTPS transport (design 8.1): `git http-backend` behind a reverse proxy validating a device-scoped bearer token and setting `REMOTE_USER`. Independent test coverage (a valid token's push/fetch succeeds, an invalid or revoked one is rejected) rather than folding into task 5's one required SSH-path test, per the scope note above.
7. Per-tenant pod isolation (ADR-0009 + ADR-0010, design 8.2/8.3): the control plane provisions a `podman pod` per tenant (a Kubernetes `Pod` later, same mechanism) instead of task 5/6's single shared filesystem; the front door proxies to that pod's own `git http-backend` over the network rather than running git commands locally. ADR-0010's own design pass decided: pods start on-demand per tenant with an idle-teardown reaper, overridable per-tenant to `always_warm`; each pod runs `wkp-hub` itself in a new single-tenant serving mode (not a second program); the front door reaches a tenant's pod by container-runtime DNS name on a shared user-defined network (not a per-tenant host-port mapping — no Kubernetes analog for that); bare repos persist on a bind-mounted shared path outside each pod's own ephemeral filesystem. Still open at implementation time: the idle-timeout value, cold-start request handling (queue vs. retryable error), and resource/cgroup quotas — see ADR-0010's own "not decided here" notes. Placing the indexing worker in its own no-network container in the same pod is expected to satisfy design 8.3's "indexing worker is a separate sandboxed process... with no network" line for free; confirm that during implementation rather than assuming it. **Human co-sign required** (container/sandbox surface, design 9.1). This task is what actually closes M5's "per-tenant hard isolation" exit criterion — M5 is not done until it lands.

## Out of scope for M5 (deferred, not forgotten)

Billing/Merchant-of-Record integration (design 8.2), the account/billing web application (design 3.3's separate, not-yet-existing repo), real hosted Postgres provisioning (a Supabase or RDS account, actual credentials), and production deployment (DNS, real TLS certificates, the actual container registry/host). All later, separate work once this milestone's CI-testable exit criterion holds -- not something any task above needs to resolve.

Later milestones are broken into tasks when the previous milestone's exit criterion holds.
