# ADR-0011: Drop the SSH transport; unify on HTTPS with mutual TLS (rustls + rcgen)

Status: accepted
Date: 2026-09-11
Design sections affected: 8.1, 8.2, 8.3
Supersedes: 8.1's D7 SSH half (`sshd` + `AuthorizedKeysCommand` + `wkp-shell`); depends on ADR-0009/0010 (pod-per-tenant model, which is what surfaced the problem below)

## Context

ADR-0009 decided per-tenant isolation is a pod per tenant, with the front door proxying to that pod's own `git http-backend` over the network -- for *both* transports design 8.1 named (SSH and HTTPS), since 8.1 already picked `git http-backend` as the one per-tenant backend implementation. That's straightforward for the HTTPS path (M5-6, PR #115): the front door is already speaking HTTP, so proxying HTTP to a tenant pod's HTTP backend is a same-protocol relay.

It is not straightforward for the SSH path. M5-7's front door terminates an SSH connection and, via `wkp-shell` (M5-3), execs `git-receive-pack`/`git-upload-pack` locally against a bare repo it can see on a shared filesystem -- that's *why* task 5's scope note (`docs/plan/milestones.md`) says M5-5 runs "against a single shared filesystem" rather than the pod model. Once repos move into per-tenant pods (M5-7, task 7), there is no local repo left for `wkp-shell` to exec against: the actual git process now lives inside a pod, reachable only over the network, speaking smart-HTTP (`git http-backend`), not the pack-protocol-over-stdio that `git-receive-pack`/`git-upload-pack` speak when exec'd directly by `sshd`. Making the SSH path work again would mean building a genuine SSH-session-to-smart-HTTP protocol bridge inside the front door: terminate the SSH session and the git pack-protocol framing it carries, translate that into smart-HTTP requests against the tenant pod's `git http-backend`, and translate the HTTP responses back into pack-protocol frames over the still-open SSH channel. This is new protocol-translation code, not a refactor of `wkp-shell`, and it does not exist anywhere in this codebase or in git's own tooling to reuse.

Given that cost, this ADR reconsiders whether to keep SSH at all, rather than building the bridge.

## Options

1. **Build the SSH↔HTTP bridge.** Keeps design 8.1's stated two-transport surface and M5-3/M5-5's already-merged, CODEOWNERS-reviewed work intact. Rejected: genuinely novel protocol-translation code (SSH channel framing to smart-HTTP request/response, in both directions, correctly handling git's pack-protocol side-band and flush-pkt semantics) is a meaningfully larger and more fragile surface than anything else M5 has built, for a transport whose only stated advantage (8.1's reasoning) was reusing OpenSSH's own hardening and CVE-scrutiny -- an advantage this option immediately gives up, since the bridge itself becomes new, unscrutinized surface sitting in front of that same OpenSSH.
2. **Keep SSH, drop the pod-per-tenant model for the SSH path only (dual isolation strategy: SSH stays on the M5-5 shared-filesystem model, HTTPS moves to pods).** Rejected: reintroduces exactly the isolation gap ADR-0009 was written to close (Unix-UID-only separation, no OS-enforced boundary) for half the traffic, permanently, and means maintaining two different isolation stories rather than one.
3. **Drop SSH entirely; keep only HTTPS, authenticated with device-scoped bearer tokens as already shipped in M5-6.** No protocol bridge needed -- the existing HTTP-to-HTTP proxy from ADR-0009/0010 already works for this transport. Rejected as the *final* state (though it's the immediate fallback if mTLS slips): a bearer token is checked by application code after the connection is already established, not at the transport handshake, which is a real security regression from SSH's key-based auth (compromise of the check itself, or a request that reaches the handler before the check runs, both become viable in a way they weren't when the identity check was the connection's admission criterion).
4. **Drop SSH entirely; replace SSH device keys with mutual TLS (mTLS) device certificates via `rustls` + `rcgen`.** No protocol bridge (one transport, HTTP, proxies cleanly to pods exactly as HTTPS already does). Authenticates at the TLS handshake, before any application code runs -- strictly stronger than option 3's bearer-token check, and closer to SSH's own security property (connection-level identity, not request-level). Pure Rust: `rustls` (protocol) + `rcgen` (the hub's own private CA, device CSR/cert issuance) keep `#![forbid(unsafe_code)]` intact (CLAUDE.md hard rule) without shelling out to OpenSSL. A *private* CA (the hub's own `rustls::RootCertStore`, never the public web trust bundle) never needs `webpki-roots` at all, which sidesteps the CDLA-Permissive-2.0 licensing reason M5-6 disabled `ureq`'s TLS features in the first place (`crates/wkp-hub/Cargo.toml`'s `ureq` entry, `default-features = false`) -- this was a constraint on trusting the *public* web PKI, which mTLS against a private CA was never doing anyway.
5. **Drop SSH; replace SSH device keys with mTLS via OpenSSL bindings (`openssl`/`openssl-sys` crate) instead of `rustls`.** Same transport-level win as option 4, but pulls in a C library and `unsafe` FFI, violating CLAUDE.md's `#![forbid(unsafe_code)]` rule in every crate except `wkp-sys`. Rejected on that basis alone; `rustls` is a mature, widely-deployed pure-Rust TLS implementation with no such tradeoff.

## Decision

**Drop the SSH transport entirely -- no bridge, no dual-transport support -- and replace SSH device keys with mutual TLS device certificates, implemented in pure Rust via `rustls` (TLS protocol) and `rcgen` (key/cert generation; the hub runs its own private CA).** Option 4 above.

The device-side security property carries over unchanged from SSH: a device still generates its own keypair locally (the same OS-keystore pattern M4-2/M5-2's `wkp hub register` already established for its ed25519 identity) and only ever submits a CSR (public information) to the hub; the private key never leaves the device, exactly as today. What changes is the wire protocol and where the hub keeps the corresponding trust material -- an ed25519 keypair whose public half the control plane stores directly (M5-2/M5-3) becomes an ed25519 (or equivalent) keypair whose public half is instead wrapped in an X.509 certificate the hub's own CA issues and can revoke.

This is a decision in principle, not a finished design. The following are real open work this ADR deliberately leaves for implementation, matching ADR-0009/0010's own practice of leaving specifics unresolved:

1. **TLS termination for `wkp-hub`'s HTTP server.** Does not exist today -- M5-6 shipped deliberately as plain HTTP (bearer-token auth only, no transport encryption at all yet). This ADR adds real `rustls`-based termination for the first time.
2. **Where the hub's own CA private key lives.** The hub becomes its own certificate authority (an `rcgen`-generated root cert), and unlike a device, the hub has no OS keystore to lean on for its own most sensitive secret. Not decided here: a `0600` file (matching `device_identity`'s existing file-fallback pattern) is the obvious starting point, but this is a genuinely new "server holds its own root secret" problem this design has not had before and deserves its own thought during implementation, not a default assumed here.
3. **Device enrollment changes.** `wkp hub register`'s RFC 8628 flow (M5-2) needs to submit a CSR and receive a signed certificate back from the hub, instead of uploading a raw public key.
4. **`handle_git_http` (`crates/wkp-hub/src/http.rs`, M5-6/M5-7) needs to replace bearer-token validation with `rustls` client-certificate verification** -- a custom `rustls::server::danger::ClientCertVerifier` (or the stable equivalent at implementation time) that checks both chain validity (signed by the hub's own CA, not the public web PKI) and the control plane's own `revoked_at` state, since standard TLS chain validation alone has no notion of that column. Standard TLS revocation mechanisms (CRL, OCSP) are not required reading here -- the control plane's own device table is already the revocation source of truth today (M5-2/M5-3) and this ADR keeps it that way, just consulted from the TLS verifier instead of from application code.
5. **`control_plane::Device`'s schema likely changes shape** (`crates/wkp-hub/src/control_plane/schema.rs`): `bearer_token_hash` becomes obsolete once mTLS is the only auth mechanism, and the stored public-key material's shape may change (raw key vs. issued certificate, or both during a transition). Exact fields not decided here.
6. **Existing, already-merged, CODEOWNERS-reviewed SSH-path code becomes obsolete and needs removal**, sequenced *after* the mTLS replacement is built and proven working -- never create a window where neither transport is functional:
   - `crates/wkp-hub/src/wkp_shell.rs` (M5-3, PR #103)
   - `deploy/hub/sshd_config`, the entrypoint's sshd bits, and `wkp-hub-akc.sh` (M5-5, PR #112)
   - `deploy/hub/test-ssh-integration.sh` and its CI job (PR #114)
   - the `authorized-keys-command`/`git-shell` CLI subcommands in `crates/wkp-hub/src/main.rs`
7. **The milestone's own top-level exit criterion** (`docs/plan/milestones.md`'s M5 table row, currently "integration test: register, push, revoke, push-must-fail" scoped to the SSH path per the M5 scope notes) needs rewriting for the mTLS path instead -- tracked as a separate documentation task, not part of this ADR.

## Options considered and rejected

See "Options" above (1, 2, 3, 5) for the rejected alternatives and why; summarized:

- **Build the bridge (1):** novel, fragile protocol-translation surface disproportionate to the transport's remaining benefit.
- **Split isolation strategy by transport (2):** permanently reintroduces the Unix-UID-only gap ADR-0009 closed, for half the traffic.
- **Bearer tokens only, no mTLS (3):** real security regression from SSH's connection-level auth to a post-handshake application check; kept only as the transitional state while mTLS lands, not the end state.
- **mTLS via OpenSSL bindings (5):** violates CLAUDE.md's `#![forbid(unsafe_code)]` rule for no offsetting benefit over `rustls`.

## Consequences

- **One transport, one auth mechanism.** The front door's proxying logic (ADR-0009/0010) stays exactly what it is today -- an HTTP relay to a tenant pod's `git http-backend` -- with no protocol bridge ever needed. This is the main win motivating this ADR.
- **Stronger authentication than either predecessor.** mTLS authenticates before any application code runs, unlike M5-6's bearer-token check (reachable, even if rejected, by any connection regardless of validity) and arguably stronger than SSH's own `AuthorizedKeysCommand` round-trip (a network call to the control plane per connection attempt, versus a local chain-and-revocation check the front door can do without necessarily calling out per request, depending on implementation).
- **New root-of-trust responsibility for the hub.** Running a private CA is new operational surface (item 2 above) with no precedent in this codebase -- device identity has always been something only the device holds, never something the hub issues and must protect the signing authority for.
- **A deliberate transition window.** Items 3-6 above are sequenced work, not a single PR: CSR-based enrollment and `rustls` termination must exist and be proven working *before* SSH code is deleted, so the hub is never left with zero working transports mid-migration.
- **CODEOWNERS/human-co-sign scope unchanged.** Every piece of this (items 1-6) touches `crates/wkp-hub/`, `deploy/`, and/or `docs/design/` -- all already CODEOWNERS-gated paths (design 9.1, `agent-wkp-m5-progress` memory's own note on this). No new review-process decision needed, just continued application of the existing rule.
- **`docs/plan/milestones.md` needs a real rewrite, not just this ADR.** The M5 top-level exit criterion, task 3 (`wkp-shell`) and task 5 (SSH integration test)'s status, and task 7's "SSH bridge" framing all need updating to reflect that the SSH path is being removed rather than proxied-to. Tracked as follow-up documentation work, not resolved by this ADR alone.
