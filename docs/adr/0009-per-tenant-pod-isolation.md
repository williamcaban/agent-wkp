# ADR-0009: Per-tenant hard isolation via container-runtime pods, not `podman exec`

Status: accepted
Date: 2026-09-09
Design sections affected: 8.1, 8.2, 8.3

## Context

Design 8.2 already names two options for per-tenant isolation: "a bare repo under its own Unix user (or a per-tenant user namespace in the container runtime)." M5-3/M5-4 built the first half of the Unix-user option -- `wkp-shell` restricts a connecting key to its own tenant's fixed bare-repo path -- but never actually drops privileges to a per-tenant UID before running `git-receive-pack`/`git-upload-pack`; every tenant's git process runs as the same user inside one shared container. The milestone's own top-level exit criterion (`docs/plan/milestones.md`) names "per-tenant UID" explicitly, so this gap needs a real decision before M5 can be considered done, not just an app-level path check.

While scoping M5-5 (the hub container task), a candidate fix -- the control plane starting one container per tenant, with the front-door `sshd`/`wkp-shell` process reaching into it via `podman exec` to run the actual git command -- was raised and rejected: `podman exec` is a container-runtime-specific mechanism with no equivalent primitive a Kubernetes-hosted deployment could use the same way (`kubectl exec` is an operator/debugging tool, not something a running service is meant to shell out to for normal request handling). Whatever mechanism is chosen needs to work identically whether the hub runs as podman pods on a single host or as pods in a Kubernetes cluster later, without a rewrite.

## Options

1. **Status quo: single shared container, Unix-UID-only isolation.** Lowest effort, but never actually satisfies the milestone's own "per-tenant UID" criterion -- the isolation boundary today is purely `wkp-shell`'s application-level path restriction (design 8.1), not an OS-enforced one. A bug in `wkp-shell` or the git subprocess it launches has no second barrier.
2. **One container/pod per tenant, `podman exec` from the front-door process into it.** Real namespace-level isolation (filesystem, and optionally network/cgroup) between tenants. Rejected: not portable to Kubernetes, where the equivalent of "exec a command in a running pod from another service" is not a supported request-serving pattern (`kubectl exec` requires cluster-API access and is built for interactive/debugging use, not a hot path). Building the front door around a mechanism with no Kubernetes equivalent means a full rewrite of the routing layer to move off single-host podman later.
3. **One container/pod per tenant, communicating over the network via `git http-backend`.** Design 8.1 already picked `git http-backend` (git's own smart-HTTP CGI program) as the HTTPS transport's backend. Reusing it as the *only* per-tenant backend, for both transports, means: the front-door `sshd`/`wkp-shell` process, after resolving a key to a tenant and deciding `git-receive-pack` vs `git-upload-pack`, does not run that command itself and does not exec into anything -- it opens a plain network connection to that tenant's own `git-http-backend` (a `podman pod`'s shared network namespace exposes it as `localhost:<port>`; a Kubernetes `Pod` exposes it via its own IP or a `ClusterIP` Service -- identical client code either way) and proxies the SSH side's git pack-protocol bytes as the equivalent smart-HTTP request/response. One backend implementation instead of two, and the front door's only runtime dependency is "can open a TCP connection to an address," which every container orchestrator supports the same way.
4. **`git-daemon` (git's anonymous `git://` protocol) per tenant, over the same shared-namespace networking as option 3.** Simpler wire protocol than smart-HTTP, but non-standard next to option 3 (which reuses git's own designed-for-this CGI program) and unauthenticated at that layer -- acceptable only if the pod-internal network is genuinely unreachable from anywhere but the front door, which still has to be true for option 3 anyway, so option 3 is strictly the safer choice for the same networking assumption.
5. **An RPC framing (gRPC, a message queue) between the front door and a per-tenant backend service.** Rejected: git's pack protocol is a streaming binary format; wrapping it in RPC framing adds real complexity (chunking, backpressure, error-mapping) for no benefit over speaking the protocol git itself already defines a wire format for.

## Decision

Per-tenant hard isolation is a **container-runtime pod per tenant** (a `podman pod` for a single-host deployment, a Kubernetes `Pod` later, without a mechanism change), not a shared container with Unix-UID separation and not `podman exec`. The front-door process (`sshd` + `AuthorizedKeysCommand` + `wkp-shell`, still a single instance handling every tenant's initial key lookup, since routing has to happen before a specific tenant's backend can be chosen at all) communicates with a tenant's pod over the network, speaking git's own smart-HTTP protocol against that pod's `git http-backend` -- option 3 above. This is **not decided in this ADR**: the pod's actual lifecycle policy (started on first connection vs. always warm, idle-teardown timing, per-pod resource/cgroup quotas) and its provisioning path (how `wkp-hub tenant create` grows from "make a directory" to "start a pod"). Those need their own design pass and are tracked as a follow-up task, not folded into M5-5.

M5-5 itself (the hub container + hardened `sshd_config` + the milestone's one required integration test) is **rescoped** to the front-door container only, against a single shared filesystem, with no pod-per-tenant routing yet -- see `docs/plan/milestones.md`'s M5 scope notes. The milestone's literal "per-tenant UID" exit criterion is therefore deferred past M5-5 to that follow-up task; M5 as a whole does not fully close until it lands.

## Consequences

- Placing each tenant's indexing worker in its own no-network container in the same pod, once the pod-per-tenant model lands, satisfies design 8.3's already-stated "indexing worker is a separate sandboxed process (Landlock + seccomp) with no network" hardening line for free -- the pod's own network namespace does the sandboxing, no syscall-level Landlock/seccomp code needed in `wkp-hub` itself. Revisit whether that's sufficient once the follow-up task's design pass happens; it may still be worth adding as defense in depth.
- The front door's request path changes from "run a local subprocess" to "proxy a network connection," a small but real latency and failure-mode change (a tenant pod being cold-started or unreachable is now a distinct error case `wkp-shell`/the front door must handle, not something a local `Command::new` failure covers). CLAUDE.md's own latency gate (non-negotiable priority 1) needs a benchmark once this lands, not just at container-build time.
- Pod lifecycle and provisioning ("who starts a tenant's pod, when, and who tears it down") is genuinely new control-plane surface -- the control plane goes from "own a Postgres row and a directory" to "own a Postgres row and a running (or startable) pod," which is a bigger change to `wkp-hub`'s own responsibilities than anything built so far in M5. This is exactly why it is not bundled into M5-5.
- Until the follow-up task lands, the isolation boundary between tenants remains what M5-3/M5-4 already built: `wkp-shell`'s application-level path restriction inside one shared container. That gap is now recorded here rather than silently accepted.
