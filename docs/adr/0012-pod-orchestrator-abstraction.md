# ADR-0012: Pluggable pod orchestrator (podman today, Kubernetes later)

Status: accepted
Date: 2026-09-11
Design sections affected: 8.1, 8.2, 8.3
Depends on: ADR-0009 (pod-per-tenant isolation, "must work the same way under Kubernetes later, without a mechanism change"), ADR-0010 (pod lifecycle and addressing)

## Context

ADR-0009 rejected `podman exec` as the front door's mechanism for reaching a tenant's pod specifically because it has no Kubernetes equivalent a running service can call on its hot path, and required whatever mechanism replaced it to "work identically whether the hub runs as podman pods on a single host or as pods in a Kubernetes cluster later, without a rewrite." That requirement was satisfied for git *traffic*: `proxy_to_tenant_pod` (`crates/wkp-hub/src/http.rs`) only ever opens a plain network connection to a tenant pod's own `git http-backend`, which is identical under either runtime.

It was not satisfied for pod *lifecycle*. `crates/wkp-hub/src/tenant_pod.rs`'s `start_pod`/`stop_pod` -- called directly from `handle_git_http`'s on-demand cold-start path (`http.rs`), the `start-pod`/`stop-pod`/`reap-idle-pods` CLI subcommands (`main.rs`), and the idle reaper (`reap_idle`) -- call `Command::new("podman")` directly, with no seam a Kubernetes backend could occupy later without touching every one of those call sites. This surfaced concretely while wiring M5-13's mTLS integration test into CI (#126): the front-door container image (`deploy/hub/Containerfile`) has no `podman` binary at all, so `handle_git_http`'s on-demand pod-start -- the *primary* production code path a tenant's first request after an idle-reap takes -- fails with `ENOENT` inside that container, not just in the test. Fixing that requires deciding how the front-door process reaches a container-runtime control plane at all, which is exactly the question ADR-0009/0010 left open ("How `wkp-hub tenant create` grows from 'make a directory' to 'start a pod'" -- ADR-0009's own follow-up note).

## Options

1. **Fix the container image (install `podman`/`podman-remote`, mount the host's socket) and leave `tenant_pod.rs`'s call sites unabstracted.** Cheapest fix for the immediate CI failure. Rejected as the only change: leaves the exact gap ADR-0009 flagged -- a Kubernetes deployment would need to rewrite `handle_git_http`, `main.rs`'s three pod subcommands, and the reaper, instead of adding one new implementation behind an existing seam.
2. **A `PodOrchestrator` trait in `wkp-hub`, with a `PodmanOrchestrator` implementation now and a reserved (not yet implemented) Kubernetes variant.** Every existing call site depends on the trait, not on `Command::new("podman")` directly. The concrete backend is chosen once at process start (`WKP_HUB_POD_ORCHESTRATOR` env var, default `podman`) and threaded through as a `Box<dyn PodOrchestrator>` / `Arc<dyn PodOrchestrator>`. Selecting `kubernetes` today is a clear startup error, not a silent no-op or a half-built stub -- there is no Kubernetes client code in this repo yet, and CLAUDE.md's "no half-finished implementations" rule means the seam should exist without a fake implementation behind it. Chosen: this is the direct fix for the gap in Context, costs one trait and one call-site threading pass, and does not require writing any Kubernetes-facing code today.
3. **A separate helper binary (`wkp-hub-orchestrator`) that `wkp-hub` shells out to, itself dispatching to `podman` or a Kubernetes client depending on its own environment.** Same pluggability as option 2, but adds a second binary, a second process boundary, and a serialization format between them for no benefit over an in-process trait -- `wkp-hub` is already the "small tool" in question (`start-pod`/`stop-pod` are already its own subcommands); wrapping it in another process just to switch on an env var it could read itself is unjustified indirection. Rejected on CLAUDE.md's "slim core" priority.
4. **Out-of-process orchestration: an external controller (a real Kubernetes operator, or a script) provisions pods and `wkp-hub` only ever proxies traffic, never starts anything itself.** Removes the lifecycle problem from `wkp-hub` entirely. Rejected for this milestone: ADR-0010 already decided the front door itself owns the on-demand cold-start/idle-reap policy (design section 8.2's "micro-SaaS scale" framing -- most tenants inactive most of the time, so lifecycle needs to react to traffic, not run on an external operator's own schedule). Revisiting that split is a larger design change than this ADR's scope.

## Decision

**Introduce `PodOrchestrator`, a trait in `crates/wkp-hub/src/tenant_pod.rs` capturing exactly the two operations every call site needs (`start_pod`, `stop_pod`), with one implementation today (`PodmanOrchestrator`, the existing `Command::new("podman")` logic, unchanged in substance) and a reserved name for a future Kubernetes implementation.** Option 2. `tenant_pod::orchestrator()` selects the implementation from `WKP_HUB_POD_ORCHESTRATOR` (default `"podman"`); `"kubernetes"` is recognized as a reserved, not-yet-implemented value (a clear startup error, matching CLAUDE.md's stance against half-finished implementations) rather than either silently falling back to podman or exposing a hidden second flag with no real backend.

`handle_git_http`, the `start-pod`/`stop-pod`/`reap-idle-pods` CLI subcommands, and `reap_idle` all take `&dyn PodOrchestrator` (or hold one behind an `Arc` in `FrontDoorState`, resolved once at server start) instead of calling `tenant_pod::start_pod`/`stop_pod` as free functions.

**Separately, and regardless of this abstraction:** `deploy/hub/Containerfile`'s runtime stage needs an actual way to reach a podman engine (installing `podman-remote` and bind-mounting the CI/host's rootless podman socket, `CONTAINER_HOST` pointed at it) for the `PodmanOrchestrator` backend to work when `wkp-hub serve` runs inside that container at all -- the trait doesn't change what the concrete podman backend needs to actually execute successfully, only where a second backend could later be added. That deployment fix is tracked as its own follow-up alongside this ADR's code change, not decided here in detail (mount path, socket activation, and any additional container capabilities are implementation specifics for that PR).

**Not decided here:** the actual Kubernetes implementation (client library choice, authentication to the cluster's API server, RBAC scope) -- reserved as a name, not designed. Per-tenant resource/cgroup quotas under either backend remain #110/M5-7's own open design-pass item, untouched by this ADR.

## Consequences

- `tenant_pod.rs`'s public surface changes from two free functions (`start_pod`, `stop_pod`) plus `reap_idle` to a trait, one concrete implementation, and a selector function; every caller (`main.rs`, `http.rs`, `front_door.rs`) threads a `&dyn PodOrchestrator` instead of calling the module directly. This is a larger diff than the container-only fix (option 1) but touches only call sites already coupled to `tenant_pod`, not new surface elsewhere.
- Selecting `WKP_HUB_POD_ORCHESTRATOR=kubernetes` today fails fast at startup with a clear message, rather than pretending to work. A future PR implementing the Kubernetes backend removes that error path by giving it a real implementation -- it does not need to touch `handle_git_http`, the CLI subcommands, or the reaper again.
- The concrete container-socket-access fix for the `podman` backend (installing `podman-remote`, mounting a socket) is deploy-surface, CODEOWNERS-gated per CLAUDE.md, same as any other `deploy/` change -- tracked and reviewed as its own PR, not folded into this ADR's trait-introduction change.
- No behavior change for the existing single-host podman deployment this milestone targets: `PodmanOrchestrator`'s methods are the prior `start_pod`/`stop_pod` logic, unmodified in substance, just reachable through the trait instead of directly.
